## 二、架构与运行边界：ESP / 平板 / 浏览器各干什么

> 合并原 Q4、Q13、Q18、Q25、Q26、Q28、Q34、Q43、Q57。核心一句话：**ESP 是服务器（文件来源 + USB Host + 灯带 + 协议端），平板浏览器是客户端（下载并运行、渲染、存数据）。**

**“网页在 ESP 里” vs “在平板浏览器里”——两个都对，是服务器/客户端分工：**

- **ESP32 = 服务器**：网页**文件**（HTML/JS/CSS，gz 后约 426.5 KiB）存在 ESP32 的 LittleFS（2.875 MiB 分区）并由它提供；它同时是 USB Host（读钢琴 MIDI）、APA102 灯带驱动、WebSocket 服务端（TCP 81）。
- **平板/手机 = 客户端**：浏览器打开 `http://192.168.4.1`，把页面**下载到本机并运行**——瀑布流（Canvas）、五线谱（OSMD SVG）都在平板的 CPU 上渲染；曲库/练习历史数据存在**平板浏览器的 IndexedDB**。
- 类比：ESP 是“菜单放在吧台”的那一方，平板是“在你桌上读菜单”的一方；你绝不会说“菜单在吧台读的”。
- 实际含义：断网但连着热点时，平板仍能重开页面（页面来自 ESP）；但换一台设备打开，曲库不会自动跟过去（数据存在原来那台设备的浏览器里）。

**为什么网页文件要放在 ESP（而不是搬进平板 App）：**

1. **零安装、随琴携带**：任何设备浏览器连上就能用，不需要装 app、商店分发、配对或版本匹配。
2. **离线自包含**：设备自己提供网页，不依赖云端或互联网，“乐器自带界面”；ESP 对 `index.html` 用 `no-cache` 每次下发（约 20 KB），对带 hash 的 JS/CSS 用 `immutable` 缓存一年（`../../firmware/src/main.cpp`），实际加载开销很小。
3. **固件+网页同版本交付**：构建产物直接输出到 `../../firmware/data`，OTA 固件/LittleFS 一起更新，避免“app 版本与固件协议不匹配”。
4. **浏览器存储按 origin 隔离**：数据存在“访问该 origin 的那台设备”（如你的练琴平板）的浏览器 IndexedDB 里，ESP 不存乐谱；同一设备上不同 origin（如 192.168.4.1 与 localhost）是两套互不串的库。注意：换设备/清站点数据，曲库不会自动跟过去，需要手动导出/恢复备份（见第四章）。

**OSMD 到底在不在 ESP 上跑？（原 Q34/Q43 的澄清）**

- OSMD（OpenSheetMusicDisplay）= 把 MusicXML 渲染成 SVG 五线谱的**浏览器排版引擎**，开源第三方（BSD-3-Clause，opensheetmusicdisplay 1.9.9，内部依赖 VexFlow/MIT，清单见 `THIRD_PARTY_NOTICES.md`）。
- 它是一份 JS 库文件（gz 约 306 KB，`../../firmware/data` 里 c-BQ4fmLDY.js.gz 305 KB 就是它），**由 ESP 托管、但被平板浏览器下载后在平板上执行**。渲染计算 100% 在平板，没有哪一步谱面渲染发生在 ESP 上。
- “放哪都一样”是对的：它是浏览器 JS，必须跑在浏览器环境里，跟文件托管在 ESP 还是平板无关；OSMD 本身完全可以原样打包进一个平板 App（Studio 路线，见第七章）。
- 自研的是另一层：`musicxml.ts`（把 MusicXML 解析成时间线：拍号/变速/反复跳转/移调）和 `sheet.ts`（包装 OSMD：跟随光标/移调/宽度自适应）。语义解析自研，画面渲染用 OSMD。

**协议 v6（原 Q28）**：ESP32 固件与网页/前端之间通信的 WebSocket JSON 协议（TCP 81 端口），**已经实现并在用**（固件 `../../firmware/src/main.cpp`、网页 `../../web/src/protocol.ts` 与自动测试）。前端发 `hello` 握手（含 v6、热点密码/启动令牌鉴权），之后都是 UTF-8 JSON——`midi`（按键事件，含高分辨率力度 `vh` 与 USB 回调单调时间戳）、`control`（踏板）、目标灯（音符语义而非像素帧）、校准、诊断、OTA 等。`ping/pong` 还会返回 ESP32 时钟，网页选最低 RTT 样本把硬件采集时刻映射到谱面时钟，让 Wi-Fi 逐包抖动不直接污染评分与录音；异常或旧固件会安全降级。它不绑定内置网页——Studio 已可配置独立 Core 地址并直接使用同一协议，所以“给独立前端连接”已经有构建和测试证据。

**能插 SD 卡吗？（原 Q13）**：ESP32-S3 芯片本身支持 SDMMC/SPI SD，但仓库里**没有任何 SD 代码**（搜不到 sdmmc/sd_card/FFat），当前存储就是一个 LittleFS 分区放网页；SD 卡未实现。且“放到平板”已经是事实——你的平板就是浏览器端，不需要装东西。

**为什么要做轻量（原 Q57，2026-08-07 更新）**：轻量不是目的，是“同样的正确性、更小的代价”；但用户已确认方向——**这套 Core 保留当底座，平板端另做独立的“牛逼”前端（Studio）**。轻量只对“ESP 内置网页”这个形态有意义，对平板本地 App 不构成限制：

- 轻量对比只适用于 Core 形态：网页从 ESP 热点下载，全包 gz 约 426.5 KiB vs 嵌入 webmscore 的 24.2 MB，决定“任何设备连热点打开页面”是 1 秒还是几十秒。这个对比对“ESP 内置网页（兜底/临时设备）”成立。
- 但你说得对：**这些东西完全可以放到平板上**。平板端一旦做成本地 App/壳，就不需要从 ESP 下载——webmscore（24 MB）、大曲库、GPU 特效都能放平板本地，ESP 存储/带宽不再是限制，平板端可以“做重、做好看”。
- 轻量解析是纯 TS，不背 24 MB WASM，未来无论浏览器、App 壳还是桌面 Studio 都能原样复用（Core 的逻辑层可直接搬到 Studio，不重写）。
- 开源定位：别人可能用手机、旧平板、低端设备，Core 轻量让整套系统门槛低。
- 结论：**轻量是 Core 的属性，不是平板 Studio 的属性**——Core 当“随琴携带的兜底/基础版”，平板 Studio 当“练琴主力体验”。

**轻量有没有牺牲性能和功能？（2026-08-07）**：结论——**关键路径性能没有牺牲（反而更快），功能上有明确上限，其中两处是真因轻量而砍、在平板 Studio 上都能解除**。

- 性能：没有牺牲。加载（426.5 KiB vs webmscore 24.2 MB，差约 58 倍）、内存/耗电（纯 TS、不背 WASM）、关键路径（瀑布流 Canvas 2D + rAF，手机浏览器 60fps；典型钢琴谱解析快）都是轻量带来的优势；协议用“音符语义”而非像素帧，带宽也更小（这是为效率而轻，不是牺牲）。
- 功能上限分三类：
  1. **目标定位裁剪（不是轻量牺牲）**：只做钢琴谱练习时间线（双行谱、标准节奏），不做全乐器/总谱/吉他谱/鼓谱、不做装饰音/复杂连音/歌词/指法排版——练琴用不到（见 9.2 与 Q58）。
  2. **体积约束（真因轻量而砍，Studio 可补）**：webmscore（24 MB）不塞 Core → 不支持 .mscz/.gp 原地转换；超大曲库索引、复杂音频分析留给 Studio。
  3. **保护性上限（防滥用，非性能瓶颈）**：录制单次 20 万事件/4 小时（`../../web/src/performance.ts` 实测）、历史最多 500 次 × 2 万事件（`../../web/src/analytics.ts` 实测）；练琴场景足够大，App 本地存储后可以放宽。
    - 正确性取舍：1016 语料中 3 类规则 / 4 个文件预期拒绝（反复结尾编号自相矛盾、跳转目标只有可见文字/无机器可读 segno 等）——宁拒绝不猜，是质量原则不是轻量牺牲（见 9.2）。
- 对 Studio 的含义：轻量解析器仍有用（快、离线、不背 WASM），Studio 可“轻量解析为主 + 遇不支持再调 webmscore”双轨；录制/历史上限可放宽；视觉特效在平板本地放开做。



**功能层内部：有没有为“轻量”牺牲性能和功能？（2026-08-07，源码核实）**：结论——**功能层长处（正确性/组合）没有为体积而缩水；真正的“轻”代价是工程简化（无 Web Worker、解析/哈希/备份全在主线程同步），表现为“大输入时短暂卡 UI”，不是功能缺失，平板 Studio 用 Worker 即可解除**。

- 没牺牲的：正确性没有缩水。MusicXML 时间线解析是自研纯 TS、确定性、可逐字节测试（1016 语料门禁 + 3 个 W3C 固定语料按 SHA-256 钉死）；判分/跟弹/移调/反复跳转语义都在，轻量化没有砍掉任何功能。关键路径反而有性能意识：跟弹排程预索引 + 二分查找（`practice.ts` 的 FollowAccompanimentPlanner）、速度换算去重 + 尾部回溯（`musicxml.ts` 的 tempoConverter）、IndexedDB 按 `by_sha256` 索引查重（O(1) 而非全表扫描）、ZIP 炸弹解压前先校验声明尺寸（`musicxml.ts` 的 assertSafeZipSize）。
- 真正的“轻”代价 = 工程简化（为简单而轻，不是为体积而轻）：
  1. **没有 Web Worker**（全库搜 `new Worker` 为 0）：`parseMusicXml()` 是同步函数、`sha256Hex()` 是自研同步实现、备份导出/校验的 base64 与哈希也在主线程——导入/批量导入/备份校验时，大谱（上限 32 MB）或大曲库会短暂冻结 UI。典型钢琴谱几十 KB、几毫秒解析完，无感；这是当前形态唯一真实存在、但练琴场景基本碰不到的性能取舍。
  2. **判分时间窗（已解除原产品简化）**：`judgement.ts` 按每个和弦所在位置的真实拍间隔生成提前/延后窗口，提供宽容/自适应/严格三档；窗口保存在乐谱时间轴，因此 25%–200% 变速仍保持相同音乐比例。快速重复同音会再按相邻同音间隔的 48% 收紧，避免一次按键串到前后目标；无有效拍点时才安全回退到确定性默认值。和弦分组窗 55 ms 仍是“近同时起音”的明确语义边界，不是判定容差。
  3. **保护性上限（安全阀，非性能瓶颈）**：录制 20 万事件/4 小时、历史 500 次 × 2 万事件、单谱 32 MB/备份 128 MB/1000 首——防滥用防锁死，练琴场景足够大（上一段已列）。
- 真正因“体积/轻量”而砍的功能（不是性能）：webmscore（24 MB）不塞 Core → 无 .mscz/.gp 原地转换、无全乐器覆盖；钢琴子集之外覆盖面（装饰音/复杂连音/歌词/指法排版）。见第九章与上一段。
- 对 Studio 的含义：功能层模块（musicxml.ts、library.ts、practice.ts、judgement.ts 等）是纯 TS、不依赖 DOM，Core/PWA/原生壳已经共享同一动态判定行为；后续在 Studio 加 Worker/批处理队列/原生存储索引即可解除“大输入卡 UI”，webmscore 双轨可补格式覆盖面。**结论：长处在、没缩水；当前剩余取舍是“大输入的流畅性”与“覆盖面”，不是实时判定精度。**


## 三、网络连接：热点 vs 家庭 Wi-Fi

> 原 Q1。两种都支持，默认开热点；AP+STA 可并存。

- ESP32 始终建立一个密码保护的 `NoteFall-88` 热点，固定地址 `http://192.168.4.1`（WebSocket 端口 81）。
- 如果网页写入家庭 Wi-Fi 凭据，设备会同时以 STA 模式接入路由器，可用 `notefall.local` 访问；热点仍保留作为恢复入口。

| 维度 | 热点模式（默认） | 家庭 Wi-Fi（STA） |
|---|---|---|
| 可用性 | 固定 IP、不依赖路由器/mDNS/互联网，开箱即用 | 依赖路由器；需关闭 AP 隔离；mDNS 不一定能解析 |
| 手机上网 | 连热点后通常失去互联网（除非用蜂窝） | 手机保持家庭网络和互联网 |
| 覆盖 | 受 ESP SoftAP 限制（范围、并发小） | 靠路由器，覆盖更好 |
| 安全 | SoftAP 内自动授权 | STA 默认只读，需热点密码解锁；重叠子网按不可信处理 |

**哪个好？** 练琴场景两者都够用，因为“按键→灯”的即时反馈是钢琴 USB 直连 ESP32 的，**根本不经过 Wi-Fi**。网页仍通过 Wi-Fi 接收按键来显示和判分，但使用 ESP32 USB 回调的硬件采集时间，经最低 RTT 时钟同步后映射到谱面时钟；因此逐包排队抖动不会直接变成假早/假晚。目标灯提前 0.3–2 秒下发，跟随伴奏由 ESP 固定队列执行。

- 日常在家：推荐 STA（手机不用切网、有互联网），体验最好。
- 首次使用、外出、路由器不稳定、mDNS 解析不到：用热点最稳。
- 设计取向：热点永远在（恢复入口），STA 可选便利；STA 侧默认只读是安全边界。

## 四、存储与录制：曲库 / 历史 / 录制存在哪、能存多少

> 合并原 Q6、Q18、Q24。

**存储位置（数据在浏览器本地，不在 ESP）：**

| 数据 | 存储位置 | 备注 |
|---|---|---|
| 曲库（乐谱+文件夹） | 浏览器 IndexedDB（当前 origin，如 http://192.168.4.1） | SHA-256 内容去重；可导出/恢复 JSON 备份 |
| 练习历史 | 另一个独立 IndexedDB | 最多 500 次，每次最多 20,000 个判定事件；单独导出 JSON |
| 常用练习选项 | localStorage | 刷新后保留 |
| 安装向导状态 | localStorage | — |
| 控制令牌 | sessionStorage | 本次 ESP 启动有效，不持久 |
| ESP 的亮度/灯位/Wi-Fi 配置 | ESP32 NVS | 不在浏览器备份中 |

**“曲库在 ESP 的网页里还是手机浏览器里？”（原 Q18）**：网页文件在 ESP32 LittleFS（由 ESP 的 HTTP 服务器提供），曲库数据在**当前页面 origin 下的浏览器 IndexedDB**（`../../web/src/library.ts`）。含义：曲库跟着“访问 origin 的浏览器/设备”走，不是跟着 ESP 走——换设备/清站点数据不会自动迁移，页面提供了“导出/恢复曲库备份（JSON）”和“导出练习历史 JSON”两个独立入口。练琴要长期用同一台设备，或定期导出备份。

**录制**：只在浏览器**内存**中（`PerformanceRecorder` 的数组），需要手动导出为标准 MIDI 文件下载；**不会自动存入曲库**，关掉页面/浏览器即丢失（除非已导出）。锁屏/切后台会确定性停止并保留当前录音供下载。

**4 小时/20 万事件**：是**单次录制**的上限（每次录音分别计），不是总量，目的是防止误开录制后无限占用内存。

- 对练琴来说足够大：一首普通曲目通常只有几千个事件；高密度演奏约 10–20 事件/秒，20 万事件也约等于数小时连续弹奏。
- 达到上限会自动停止并明确提示，上限前已录部分仍可完整下载；要更长就导出后重新开始（录制本身不自动持久化，没有“总量”概念）。

**能存多少乐谱/MIDI（原 Q24）**：容量取决于浏览器配额（Chrome 类通常约磁盘 60%，实际几百 MB 到数 GB），页面会显示“已用空间/配额/持久化状态”。普通 MusicXML 文本约 10–100 KB（测试语料单文件 1–6 KB），MIDI 几 KB 到几十 KB；按平均 50 KB/首，1 GB ≈ 2 万首，200 MB 也能放约 4000 首。**瓶颈不在容量，而在浏览器清理/私密模式/换设备**（IndexedDB 不是永久保证）。
## 五、练习功能详解：等我弹 / 实时 / 跟随我 / 左右手 / 变速 / 移调 / A–B 循环

> 合并原 Q5、Q15、Q16、Q17。

**七个概念速览（原 Q5）：**

- **等我弹（Wait）**：目标**和弦**必须同时物理按住且没有仍按住的错误键才算命中；逐个点按松开的音不记分，提前松键会撤销暂存命中，重复按同一个正确音不重复计分。正确和弦保持期间松开错误键，立即整组提交并推进。
- **实时（Realtime）**：默认按每个位置的局部拍速自适应判分，并可选宽容/严格档；快速重复同音自动收窄，窗口过后未命中的目标计为漏键。改变练习速度会保持相同音乐比例，面板显示换算后的现实毫秒范围；同时支持按真实拍号/速度变化/反复顺序的 Web Audio 节拍器与一小节预备拍。
- **跟随我（Follow）**：只练一只手；用户完成当前目标和弦后，另一只手由 PX-S7000 自身音源播放（经 USB MIDI OUT 本地排程），再按谱面间隔与所选速度进入下一组；若实机没有 OUT 端点，明确降级为无伴奏跟随。
- **左右手**：练习前按左手/右手/双手筛选，未选声部不进入实体目标与判分，屏幕仅低亮度保留显示。
- **变速**：25%–200% 速度，以 5 个百分点步进（25/30/35/…/200），时间线、跟随间隔与节拍器同步缩放。
- **移调**：±12 半音同步移调，五线谱/瀑布流/目标灯同步变化；曲库里原始文件哈希不变。
- **A–B 循环**：在 A–B 时间点之间循环练习，循环边界按时间轴计算；到 B 回到 A，无越界目标、不重复累计成绩。

**“等我弹”不该是“等我谈”吗？和弦是什么（原 Q15）**：你的直觉对——“等我弹”就是“程序等我弹”（你主导，它不催你），程序一直等你把当前目标音弹出来才前进，不会因为你思考久判错（`index.html` 说明：“等我弹模式不会因思考时间判错”）。提“和弦”是因为解析乐谱时把 55 ms 内同时开始的一组音归为一个 Chord（`../../web/src/practice.ts` 的 `groupChords(notes, 55)`），Wait 模式下**这一组要同时物理按住才算过**（`WaitHitBuffer` 先暂存命中，整组按住且没有多余错键才提交）。所以“和弦”不是额外门槛，而是乐谱的自然分组方式——这正是 Wait 模式对错音更严格、更贴近“真的会弹这一段”的原因。

**“跟随我”和“左右手”什么区别（原 Q16）**：一个是练习模式，一个是声部筛选，两者不冲突、可以组合用。

- **左右手**（声部筛选）：练习前选左手/右手/双手，没选的声部不进实体目标灯、不判分，屏幕上仅低亮度保留显示——这是“练哪只手”的范围设定。
- **跟随我**（模式）：只练一只手；你弹当前目标和弦，另一只手由 PX-S7000 自身音源按你的实际速度自动伴奏——这是“另一只手谁来弹”的机制。
- 组合示例：跟随我 + 只练右手 = 你弹右手，钢琴自动弹左手跟着你。

**“移调”是什么意思（原 Q17）**：把整首曲子整体升高/降低若干半音来练（范围 ±12 半音，如 +2 = 整首升高大二度），画面和灯同步变，原文件不动（曲库里原始文件哈希不变，`../../web/src/transpose.ts` 处理）。用途：旋律太高/太低换到顺手音区练、用不同调式练同一首、配合指法练习。它只是“显示与判分层面移调”，不改你导入的原谱。

## 六、亮度与供电安全：为什么硬上限 4/31、这灯多亮

> 合并原 Q3、Q11。这是故意的安全上限，不是缺陷。

- `4/31`：APA102/SK9822 的全局亮度是 5 bit（0–31），4 档约等于 12.9% 占空比；设计电流约 1.363 A，约 6.8 W @ 5 V（`../../generated/power_budget.json`）。上限硬编码在 `../../firmware/include/layout_generated.h` 的 `kMaxGlobalBrightness = 4`，网页滑块不能调更高。

原因：

1. **供电/保险丝预算**：176 像素全白不封顶约 52.8 W（约 10.6 A @ 5 V），远超 3 A 保险丝、5 V/5 A 电源和 20 AWG 线。封顶到 4/31 后灯带电流 1.363 A，整机设计电流 2.013 A（占 5 A 电源约 40%），也满足“< 3 A × 80%”设计上限；双端注电最差支路压降约 1.45%。
2. **温升与安全**：灯带紧贴琴键竖直安装，验收门禁要求满上限连续 30 分钟任一点 <55 °C，保护钢琴漆面、胶贴与灯带寿命。
3. **用途决定**：实体灯只是“下一组目标键”指示，不需要照明级亮度；4/31 在练习室足够醒目，也避免直射眩光。
4. **不可越权**：上限写死，防止误操作烧保险/过热。

**多少 nits（原 Q11）**：仓库里**没有 nits/lm/lx 实测数据**，只有供电与温升预算；APA102/SK9822 单灯珠典型光通量在数据手册里有，但仓库未引用，也没有整条灯带的照度实测。要准确数字必须在 G1 台架用光度计/照度计测。**想更亮必须重新做供电预算（保险丝/线径/电源）并通过温升验收，不能只改一个常数。**
## 七、交付形态：网页 vs App（NoteFall Studio 路线）

> **2026-08-10 当前状态**：Core 零安装网页、Studio PWA、Capacitor Android/iOS 工程均已存在并共享练习核心。Studio 可配置 Core 地址，支持单谱面、单瀑布流、分屏和沉浸全屏；Android 瀑布流是硬件加速原生 View，JDK 21/API 36 debug APK 已构建。App 是推荐的练琴平板入口；PWA 是电脑、临时设备和开发备用，二者不是要求用户同时安装的两套产品。iOS 签名/原生渲染和 Android/iOS 热点、锁屏、自动切网仍须实机验收。

- **NoteFall Core**：完整网页（HTML/JS/CSS + OSMD）存放在 ESP32 LittleFS，任何手机/平板连热点后打开 `http://192.168.4.1` 即可离线使用，是随琴兜底入口。
- **NoteFall Studio**：资源随 PWA 缓存或 App 安装包提供，通过协议 v6 连接 Core；曲库、练习引擎、弱点巡回和谱面逻辑复用同一 TypeScript 源码，Android 只把高频瀑布流渲染下沉到原生 View。
- MuseScore/Guitar Pro 原地转换、大型曲库后台分析和复杂音频仍属于 Studio 可扩展边界，不塞进 ESP 的 2.875 MiB LittleFS，也不成为日常练琴启动条件。

**“封装成 app”有什么难度（原 Q22）**：套壳容易，难在“安全上下文”和“离线可用”在 ESP 场景下冲突：

1. **PWA 离线缓存要 HTTPS**：Service Worker 只在安全上下文（HTTPS/localhost）可用，而 ESP 热点是明文 HTTP，所以“添加到主屏幕”不保证可靠离线（`../mobile-offline-and-storage.md` 明确“不要承诺 Service Worker/PWA 离线缓存”）。
2. **HTTPS App 访问局域网设备是混合内容**：未来 Studio 若是 HTTPS（商店要求），去连 ESP 的 `ws://192.168.4.1:81` 属于 mixed content，iOS/Android 策略不同可能直接拦截；要么上 WSS/可信证书（ESP 上通常没有受信任 TLS 证书），要么原生壳做桥接。
3. **原生壳工程成本**：Android 9+ 默认禁明文流量、iOS ATS、证书固定、打包签名、商店分发与更新、以及“曲库数据在网页 origin 下”迁移到 App 存储的兼容处理。
4. 文档原话（`../architecture.md`）：“外部 HTTPS PWA 访问局域网明文 WebSocket/私网设备时存在浏览器安全策略差异，因此发布前必须分别验证 iOS、Android；若策略不可控，原生壳是确定性更高的交付方式。”

**做 App/壳是不是重写（原 Q29、Q61）**：不是重写整个工程；重做的是“平板端前端”这一层，ESP 固件、协议、灯带驱动完全不动。现有网页（`../../web/` 的 TS/HTML/CSS）本身就是可复用代码，不是废稿。

- **WebView 壳（Capacitor/Tauri/PWA 壳）**：不用重写，现有网页原样装进去，只包壳；代价是渲染仍是 Web 技术，观感上限不变。工程量很小。
- **真原生（SwiftUI/Compose/Flutter/Unity）**：视觉层要重写（瀑布流/五线谱/界面约 800 行 + 交互整合），但核心逻辑层（musicxml.ts / practice.ts / protocol.ts / library.ts 等纯 TS，约 6000 行）不用重写，可编译成 WASM 或桥接复用。约等于一次中等规模前端工程。
- 所以不是“几千行全重写”，是“视觉层 + 桥接重写，逻辑层复用”。

**封装 App 算原生 App 吗（原 Q53）**：不算。封装壳（PWA/WebView 壳）里跑的仍是浏览器引擎，瀑布流/谱面渲染仍是 Web 技术；原生 App 指用平台 UI/GPU 框架（SwiftUI/Compose/Flutter/Unity 等）直接渲染。且 PWA 离线缓存要求 HTTPS，ESP 热点是 HTTP，所以 PWA 离线在当前拓扑下不可用。封装壳只是“换了个安装入口”，不是原生渲染。

**2026-08-09 选型澄清**：Studio 采用“原生安装包/生命周期/权限桥接 + OSMD 专用 WebView 谱面 + 原生 GPU 瀑布流”。Canvas/WebGL 双视图是 PWA/iOS 回退和性能对照，不冒充 SwiftUI/Compose 式真原生渲染；Android 已接入硬件加速原生 View，按系统单调时钟自行逐帧绘制，跨桥只传乐谱、状态与低频时钟校正，不传整帧像素。真正重写的是瀑布流、布局、手势与少量状态绑定，MusicXML、练习/评分、曲库、协议和 ESP 固件继续复用。性能与长期稳定门禁见 ADR-004。

## 九、开源对比：PTS / Openthesia / PLV / PianoLux

> 合并原 Q19、Q23、Q32、Q42、Q46、Q47、Q50、Q52、Q54、Q55、Q56、Q58、Q60、Q62。2026-08-10 复核结论：在 PX-S7000 单灯带琴前练习这一目标内，功能闭环、硬件链路、工程可验证性与练琴信息可视化的组合均已超过固定参考快照；Openthesia 的桌面舞台特效/VST/视频、PTS 的 MuseScore/Guitar Pro 转换等目标外能力仍分别领先，不应混为本项目缺陷。

### 9.1 开源项目都是谁

- **Piano Trainer Studio（PTS，原 Q32）**：GitHub ztbishop/piano-trainer-studio，AGPL-3.0 开源钢琴练习 Web 应用，本项目的“第一软件/产品参考”。功能：MusicXML/XML/MXL 为主格式（OSMD 渲染谱面），MIDI/MuseScore/Guitar Pro 通过 webmscore 转成 MusicXML；三种练习模式、左右手、循环/变速/移调/得分、IndexedDB 曲库与批量导入、逐键 LED 校准，产品闭环成熟。拓扑不同：PTS 靠浏览器 Web MIDI 收钢琴、发 WLED/helper 控灯；NoteFall 是 PX-S7000 USB 直连 ESP32-S3 再驱动 APA102。NoteFall 学习其产品行为，但不复制 AGPL 代码（MIT 独立实现）。
- **Openthesia（ImAxel0/Openthesia）**：Windows 桌面端，GPL-3.0，约 7600 行 C#，用 Veldrid/ImGui GPU 渲染瀑布流（粒子/拖尾/透视），主要吃 MIDI、不解析 MusicXML、不控 ESP/灯带。是“瀑布流观感”的参考标杆。
- **Piano-LED-Visualizer（PLV）**：树莓派/Linux 部署为主，成熟 SD 卡/系统服务经验，主要吃 MIDI。
- **PianoLux**：ESP32 但只做 MIDI/WS2812，无 MusicXML、无判分。

**本工程有没有他们厉害（原 Q52）**：分开说。**功能上我们有他们没有的**：谱面+瀑布双视图、三种练习模式、完整反复/跳转语义、琴内音源 Follow、历史/自适应建议、认证 OTA、参数化制造包。**观感上目前确实不如**：瀑布流是基础 Canvas（背景渐变、圆角矩形音符、左右手配色左青右粉、隐藏手变暗、对错变色、A–B 循环虚线、底部键盘状态色；没有发光/粒子/透视）。所以是“功能更强、观感更素”。

### 9.2 功能层：强在哪、他们为什么不做、和 MuseScore 系差什么

**瀑布流和乐谱相比开源强在哪（原 Q19）**：强在“组合”而不是单项——NoteFall 是唯一同时具备“五线谱 + 瀑布流双视图、真实反复/跳转语义、统一 MIDI/MusicXML 时间线、琴内音源 Follow Me、嵌入式 <500 KiB 网页”的开源钢琴灯带工程。依据 `../competitive-benchmark.md` 与 `../open-source-review.md`：

- **双视图**：PTS 只有谱面跟随（◐），Openthesia 只有瀑布流（●），PLV/PianoLux 是 ◐；NoteFall 是 ● 两种视图可切换（`view-mode`）。
- **谱面正确性**：真实反复/结尾/D.C./D.S./Fine/Coda 播放顺序、普通/复合/自由拍号、metric modulation 精确换算——PTS 也有完整反复语义，其余项目多为 ◐。
- **性能定位**：瀑布流是浏览器 Canvas + `requestAnimationFrame`，五线谱是 OSMD SVG + 自主管理的稳定阅读带逐音光标；当前嵌入资源共 436,782 B（约 426.5 KiB，门禁 <500 KiB），OSMD 压缩后约 299 KB；已在 Chromium + WebKit 的 390×844、1280×900、1600×1068 和 3200×2136 视口回归无横向溢出，并用 48 小节/240 音符双谱表合成长谱验证自动翻谱与右缘双手全曲指纹。光标会在同一小节的不同音符间移动、按当前左右手改变颜色，反复段再次演奏时回到正确的印刷小节；谱面旁同步浮现早/准/晚、错音和漏音反馈。导航上方另有 7 px 全曲练习热力带，按反复展开后的小节分别显示绿色稳定、黄色注意、红色薄弱，点击即可从该小节重练。3200×2136 全屏下画面实测高 2130 px、顶部仅 3 px，且可选择播放时自动进入全屏。瀑布流还以亮度/高光/落键帽表达目标力度，以和弦星座弧线表达近同时音与双手协调；`p`/`fff` 真浏览器探针实测亮度 163.0/219.7，跨手弧线在 Chromium/WebKit 分别检出 406/411 个有效亮像素；实时命中用自适应琴键时序尺显示早/准/晚和可容纳时的毫秒数，松键后再用青色 `↔` 或橙色 `↘/短 xx%` 给出时值反馈（Chromium 像素探针分别检出 205/147 个特征像素）；表现力洞察还把力度基准/轮廓、物理松键/踏板发声时值、精确同起点和弦展开和左右手先后分开，四个 20 ms 跨手样本在真浏览器显示“和弦 100% / 右手晚 20 ms”，并把这些指标纳入复盘、趋势、教练和弱点巡回。
- **观感诚实对比**：Openthesia 桌面 GPU 画面上限更高；NoteFall 是“能在手机浏览器跑、能随 ESP 离线携带”的轻量实现，观感目标是清晰可用，不是桌面级特效。这就是组合领先与单项上限的区别。

**功能层强项清单（原 Q56，按 `../competitive-benchmark.md` 可审计矩阵）**：USB→ESP→SPI 本地确定性链路（按键不经过浏览器/Wi-Fi）、ESP 硬件采集时间判定/录音（不受逐包 Wi-Fi 抖动直接污染）、逐和弦局部拍速自适应判定/快速同音防串匹配、MIDI+MusicXML 双格式、谱面+瀑布双视图、三种练习模式、琴内音源 Follow Me 带安全排程、完整反复/跳转语义、逐音时序/力度基准/相对强弱轮廓/物理松键与踏板发声时值/和弦展开与双手同步/历史趋势、反复安全小节热力回练、可解释单轮建议、连续达标才进阶的多片段弱点巡回、逐键灯位校准、认证 OTA+双槽更新、参数化机械/电气制造包、跨层 CI（275 项测试 + 1016 语料）。

**他们为什么不做（原 Q56）**：定位不同（Openthesia 是桌面瀑布流/音频练习，不做灯带硬件也不做 MusicXML；PLV 是树莓派主机、以 MIDI 为主；PianoLux 是 ESP 但只做 MIDI/WS2812、无 MusicXML 无判分）；成本与验证门槛高（自研 MusicXML 时间线 + 判分 + 指定琴 USB 固件，投入大且必须真琴才能验收 G2，开源作者未必有条件）；许可证（PTS 是 AGPL-3.0 传染，不能照搬，见 `../pts-adoption-decision.md`）；捷径（PTS 用 webmscore 外包转换、OSMD 外包渲染，绕开最难的解析层）。我们做是因为目标是“一台练琴平板 + 琴前灯带的完整闭环”，必须本地、离线、指定琴、谱面语义正确，这些是他们不覆盖的组合。

**MusicXML 时间线解析有人做过吗（原 Q46、Q50）**：绝对意义上当然有人更强——MuseScore（及其 WASM 版 webmscore）、Python 的 music21、OSMD 内部解析器覆盖更多 MusicXML 特性。但在“轻量、为钢琴练习判分定制、能塞进浏览器小包”这个定位上，开源钢琴灯带项目里没有现成同款：PTS 靠 webmscore 转换 + OSMD 显示，没有自己的轻量时间线层。所以“把 MusicXML 解析成时间线”不是新概念，但具体这套实现（浏览器轻量解析 + 反复/跳转语义 + 移调 + 与判分/灯/Note Off 时值对齐）是**我们的工程实现**——不是“发明了新东西”，而是“别人绕开或外包的难题，我们针对这个场景自己做了轻量版”。结论：完整度我们不如 MuseScore 系；针对性（反复/跳转/移调 + 判分对齐 + 426.5 KiB 包）我们是独一份。

**和 MuseScore 系差什么（原 Q58）**：差的是“全乐器、全记号、可打印总谱级排版”；我们只做“钢琴谱的练习时间线”。

- 乐器范围：我们只做钢琴/键盘谱（双行谱、标准节奏）；MuseScore 支持所有乐器、总谱、吉他六线谱、鼓谱。
- 记号与谱面元素：装饰音（颤音/琶音/滑音/倚音）、复杂连音嵌套、多声部、力度渐变、歌词、指法、弓法、踏板记号渲染等排版元素。
- 不规则节奏/拍号：变拍号、无拍号、极端复合连音。
    - 我们的边界（代码里有据）：1016 语料中 1012 解析、3 类规则 / 4 个文件预期拒绝——45f-Repeats-InvalidEndings（反复结尾编号自相矛盾，拒绝猜播放顺序）、Dorico MetadataTest（两个版本变体：只有元数据、无声部）、Finale RepeatsTest（D.S. 跳转目标只有可见文字、没有机器可读 segno）。原则是“不猜”：谱面矛盾/不可信时拒绝，而不是生成错误练习。
- 一句话：差的是覆盖广度，不是正确性；这些差距在“钢琴谱练琴”场景基本不碰到。

### 9.3 转换与渲染：webmscore / OSMD / “外包”

**webmscore 转换是干嘛的、为什么他们不做而我们做（原 Q54）**：转换 = 把 MuseScore（.mscz）和 Guitar Pro（.gp）这类打谱软件私有格式转成 MusicXML，练习软件才能读。他们不做是因为根本不支持这些格式（PTS 以外的项目只收 MIDI，最简单）；我们做是因为 MusicXML 才带反复/跳转等练习必需的语义。但 24 MB 的 webmscore **明确不塞进 ESP**，那部分留给未来 Studio 层（见第七章与 `competitive-benchmark.md` 的“明确不塞进 Core 的功能”）。

**webmscore 是 OSMD 吗（原 Q55）**：不是。webmscore = MuseScore 整个程序编译成 WASM（约 24 MB），能解析+排版+转换全功能；OSMD = 只负责“把 MusicXML 画成 SVG 五线谱”的显示引擎（约 306 KB gz）。webmscore 是“全能引擎”，OSMD 是“画图器”，musicxml.ts 是“轻量语义解析器”，三者不同。

**开源方案都没自己实现解析、都是“外包”？（原 Q42）**：要分开看。

- 渲染引擎：PTS 用 OSMD、我们也用 OSMD（BSD-3-Clause，opensheetmusicdisplay 1.9.9），没人自研排版引擎——自研等于重造 MuseScore，成本极高。这层确实是“共用开源库”。
- 格式转换：PTS 用 webmscore（24.2 MB WASM）把 MuseScore/Guitar Pro 转 MusicXML。Openthesia / PLV / PianoLux 主要只吃 MIDI，根本不解析 MusicXML，谈不上“外包解析”。
- 放不进 ESP：webmscore 24.2 MB 远超 LittleFS 的 2.875 MiB；OSMD gz 约 306 KB，放得进（../../firmware/data 里 c-BQ4fmLDY.js.gz 305 KB）。
    - 性能：不能说它全面比我们差。加载/体积我们完胜（整个前端 gz 约 426.5 KiB vs 24.2 MB，差约 58 倍）；典型钢琴谱解析我们更快更轻；但覆盖面 webmscore 更强（全乐器/吉他谱/总谱/极端记号），我们只覆盖钢琴谱常见子集（1016 语料里 3 类规则 / 4 个文件预期拒绝）。目标场景我们快，通用场景它强。

**一会儿说“有人做”、一会儿说“外包”，矛盾吗（原 Q60）**：不矛盾，是两层东西。“有人做”指引擎层存在成熟开源实现：OSMD（渲染）、MuseScore/webmscore/music21（全功能解析）——确实有且比我们全。“外包”指 PTS 不自己写引擎，而是直接嵌入 webmscore 和 OSMD，自己写产品逻辑（练习模式/UI/校准）。所以精确说法是：钢琴灯带开源项目里没人做“轻量时间线”这一层——PTS 也没做，它用外包引擎替代。结论：引擎“有人做”；轻量时间线“只有我们做”；PTS 的路线是“外包”。

**其他开源做到重型功能了吗（原 Q23）**：部分做到，但跑在浏览器/PC，不在 ESP——NoteFall 是故意不塞进 Core，不是做不到。PTS 确实做了 MuseScore/Guitar Pro 浏览器转换（webmscore WASM 约 24.2 MB）；Openthesia 是 Windows 桌面端，用 SoundFont/VST 发声；PLV 有成熟树莓派部署。但这些重型能力大多不在“钢琴灯带”核心链路上；NoteFall 的分层决定是 Core 只嵌日常必需资源（<500 KiB），转换引擎这类 20 MB+ WASM 留给未来 Studio。

### 9.4 概念：MusicXML vs MIDI

**MusicXML 是啥（原 Q47）**：乐谱的开放交换格式（一种 XML）。它把音符、拍号、速度、调号、反复/跳转记号等“乐谱语义”结构化存下来，让打谱、练习、渲染等不同软件互通。类比：它是“乐谱界的 docx”；.mid 只存“演奏事件”（哪个键、何时、多响），不含谱面排版和反复/跳转记号。

**和 MIDI 的本质区别（原 Q62）**：区别在“结构”。MIDI 是扁平演奏事件流，MusicXML 是乐谱结构。

- MIDI 只存：哪个键、何时按下/松开、力度、踏板；没有小节边界、没有反复/跳转记号（D.C./D.S./Coda/Fine）、没有拍号/调号语义、没有左右手声部归属（只有 channel，不保证对应手）。
- MusicXML 存：小节、拍号、调号、反复/跳转/结尾（一房子二房子）、声部/手、音符时值。
- 练习引擎需要结构才能做：D.C. al Fine 反复回开头、D.S. 跳转、一房子二房子、正确双手跟随、移调。MIDI 只是“按事件列表从头播到尾”，无法理解“这里是反复”。
- 典型例子：同一首曲子导出 MIDI，很多软件会把反复段平铺展开成两遍（或干脆丢）；MusicXML 里明确写着“反复”标记。音符事件对得上，但“结构”丢了。
- 所以不是“一个事件对应一个音符就够”——音符对，结构不对，练习模式的正确性就没了。这正是自研解析、并坚持“谱面矛盾不猜”的原因（见 9.2）。
### 9.5 “功能被裁剪的两处”具体指什么（2026-08-07）

**第一处：格式转换（不能直接打开 .mscz/.gp，要先转成 MusicXML/MIDI）**：
- 我们读入的格式只有四种：MIDI（.mid/.midi）、MusicXML（.xml/.musicxml）、MXL（压缩 MusicXML）——`main.ts` 的 `parseScoreSource()` 只认这些扩展名。
- MuseScore 的 .mscz 和 Guitar Pro 的 .gp 是各自的私有格式。要读它们，得先由 MuseScore 本体（编译成 WASM 的 webmscore，约 24 MB）做一次“格式转换”。PTS 就是把 webmscore 嵌进网页干这件事；Core 因体积门禁（<500 KiB）明确不塞，所以**拿 .mscz/.gp 直接拖进 Core 会提示不支持**，需先在电脑 MuseScore 里“导出为 MusicXML/MIDI”，或留给未来 Studio（可嵌 webmscore 双轨转换）。
- 注意：这不是“解析能力差”，是“不背 24 MB 引擎”的刻意裁剪；转换后的 MusicXML 我们解析得很快。

**第二处：钢琴子集之外的覆盖面（同样是 MusicXML，只解释钢琴谱常见子集）**：
- 即使文件本身是 MusicXML，也只建模“钢琴练习需要的那部分”：双行谱（高/低音谱表）、标准节奏、拍号/变速、反复/跳转/结尾、移调、左右手声部。
- 超出子集、不解释/不建模的：全乐器总谱、吉他六线谱、鼓谱；装饰音（颤音/琶音/滑音/倚音）、复杂连音嵌套、多声部、力度渐变、歌词、指法、弓法、踏板记号等排版元素；变拍号、无拍号、极端复合连音。
- 原则：谱面矛盾/不可信时拒绝而不是猜错（1016 语料里 3 类规则 / 4 个文件预期拒绝：45f 反复结尾编号自相矛盾、Dorico 只有元数据无声部、Finale 的 D.S. 只有可见文字没有机器可读 segno）。

**“你说 xml 不如别人”——精确说法（原 Q55/Q58）**：
- 我说的不是“MusicXML 解析整体不如别人”，而是**“覆盖广度不如 MuseScore 系”**：MuseScore/webmscore 是全乐器、全记号的通用引擎，我们只做钢琴子集。
- 但在“钢琴谱练琴”这个目标场景里，我们是**更快、更轻、正确性有语料门禁**的（目标场景我们快，通用场景它强）。所以“不如”只落在“广度/极端记号”上，不落在“钢琴谱的正确性和速度”上。

**转换功能用处大吗（2026-08-07）**：对钢琴练琴场景**用处中等偏小——它是“便利层”，不是“能力缺口”**。

- 它只省一步：让 .mscz/.gp 直接拖进应用，不用先在 MuseScore 里导出。真正读懂乐谱的活（MusicXML→时间线）我们已做，转换只是“打开私有格式外壳”。
- 拆开看：.gp 是吉他/贝斯六线谱格式，钢琴谱几乎不会用，对你基本用不上；.mscz 最可能遇到（MuseScore.com 默认下载即 .mscz、也有人自用 MuseScore 打谱），但有免费替代——桌面版/在线 MuseScore 里“导出为 MusicXML/MIDI”再拖进 Core，几秒钟。所以是“省一步”，不是“做不到”。
- 为什么 Core 不塞：webmscore 24 MB vs Core 体积门禁 <500 KiB；且覆盖广不等于转换结果都对（极端记号 webmscore 也未必完美）。
- 真正会卡住你的其实是 PDF/图片谱（很多平台只给 PDF，任何软件都需 OCR，是另一回事）；MIDI 与 MusicXML 我们本来就直接支持。所以“能不能练到想练的曲子”基本不取决于 webmscore。
- Studio 优先级建议：转换排在视觉层、Worker（大文件不卡）、原生存储之后，属锦上添花；真要做就在 Studio 双轨（轻量解析为主 + 遇 .mscz/.gp 调 webmscore），Core 不用动。


## 十、UI 与视觉差距：为什么“素”、差多少、能不能做好

> 合并原 Q8、Q27、Q30、Q31、Q33、Q35、Q36、Q44、Q45、Q49、Q51。

**界面是不是只有几个格子（原 Q8）**：代码里是完整的深色 UI，不是只有格子；但“空状态”确实显得简陋。

- 界面事实（`../../web/index.html` + `../../web/src/style.css`）：深色主题（`#080a0f` 背景 + 顶部径向渐变）、顶栏 + 状态胶囊（ESP/钢琴/伴奏/延音/验收）、一排操作按钮（导入乐谱/播放/复位/录制/模式/速度/画面/练习选项/曲库/设备设置/安装向导）、曲目信息条、下方大画布（瀑布流）或五线谱、右侧滑出面板（练习选项/我的曲库/设备设置/安装向导）都带圆角卡片和阴影。Studio 的 Core 地址只在设备设置内显示，不占演奏主页面。
- 为什么看起来“只有格子”：首次打开、还没导入乐谱时，中间大画布是空白（只有渐变色 + 微弱网格线 + 底部钢琴键盘），顶部就是一行按钮，所以视觉上主要就是“顶栏 + 几个长方形按钮/面板”。导入乐谱开始练习后，瀑布流（左右手彩色下落条、对错高亮、A–B 虚线）才铺满主区域。
- 客观评价：功能优先、移动端友好的工具型 UI（深色、可读、按钮大），不是打磨过的商业 App；空状态没有插画/引导文案是它显得“丑”的主要原因，属视觉完成度问题，不是缺功能。

**“观感朴素”指什么（原 Q30、Q35）**：主要指“整体界面 + 瀑布流”的视觉层，不是“只有几个框就没功能”；五线谱本身和开源同级。

- 整体界面：素——深色工具型 UI，首次打开只有按钮条+空画布，没有插画、引导文案、动效（空状态问题）。
- 瀑布流：功能完整（目标键、命中/错键高亮、左右手配色、A–B 虚线），但视觉是基础 Canvas 圆角矩形+网格，没有 GPU 特效。
- 五线谱：用的是 OSMD（PTS 同款引擎），渲染质量与 PTS 同级别；NoteFall 还在其上增加了 3:2 平板密度规则、全宽系统、逐音且反复安全的手别彩色光标、稳定阅读带自动翻谱，以及贴近光标的早/准/晚、错音和漏音反馈。
- 所以“素”= 界面与瀑布流的视觉打磨不足，不是功能缺失；“乐谱不素、只有瀑布流和界面素”。

**到底差多少（原 Q33）**：功能/谱面正确性上不差甚至更强（真实反复跳转、三模式判分、随 ESP 的灯带联动是开源里没有的）；**视觉上瀑布流差 Openthesia 一个档次、整体界面比 PTS 素、五线谱同级**。

| 维度 | NoteFall 现状 | Openthesia（桌面） | PTS（浏览器） |
|---|---|---|---|
| 瀑布流 | Canvas 2D，基础圆角矩形+网格，rAF 驱动 | GPU（Veldrid/ImGui）高帧率、特效、细腻排版 | 无瀑布流（只有谱面） |
| 五线谱 | OSMD SVG+光标+移调 | 无 | OSMD（同引擎，配置更细） |
| 整体 UI | 工具型深色 UI，空状态素 | 完整桌面 GUI | 成熟产品闭环 UI |
| 功能深度 | 真实反复/跳转语义、三模式判分、协议安全、逐键校准、OTA | 播放/等待/录制等 | 转换、曲库、模式齐全 |

关键：这个差距是**可独立修复的视觉层**——纯前端 CSS/Canvas/WebGL 打磨即可，不需要动 ESP 固件、协议或判分引擎。

**在平板上能超过 Openthesia 吗（原 Q31、Q36、Q45）**：不是“不可能”，是“当前没投入”。Openthesia 是 Windows 桌面 + GPU（Veldrid/ImGui）专为高帧率瀑布流写的（约 7600 行 C#）；它没有 ESP、不控灯带。平板浏览器用 Canvas/WebGL 完全可以接近甚至超越（粒子、渐变滚动、动效、流畅度都能做）；平板原生 App（GPU 渲染）更没有技术上限。这是前端视觉工程的投入问题，不是平台天花板。难度分三档：

1. **第一档（中等工作量，效果明显）**：把现有 Canvas 2D 打磨好——渐变色块、发光/高亮、命中粒子闪光、滚动缓动、更好的键盘与网格、配色与字体。约 200–400 行认真写的前端代码，任何平板浏览器 60fps 都跑得动。
2. **第二档（工作量大）**：WebGL2 shader 做粒子、模糊拖尾、透视等特效，视觉可接近甚至超过 Openthesia；可行。
3. **第三档（最大）**：平板原生 App（GPU 渲染），可控性最高、工作量最大。
4. 注：Openthesia 桌面 GPU 特效在平板浏览器上做不到 100% 复刻（它本身也不在平板上），但观感接近甚至部分超过可行，纯前端、不动 ESP。

**什么叫“排版美化”（原 Q44）**：指 OSMD 渲染时那些“观感”参数：页边距/行距、系统换行、紧凑度、字号、字体、颜色、标题、小节号、多小节休止压缩等。当前已完成 SVG 后端、标题、紧凑排版、源谱换行保留、平板全宽系统、缩放与边距、自主管理的稳定阅读带、逐音/反复安全光标和判定浮层；仍可继续优化字体主题、多小节休止压缩，以及极端复杂总谱的力度与表情记号布局。类比：OSMD 是排版机，NoteFall 不重造制谱引擎，而是在它上面加入练琴场景需要的导航与反馈层。

**排版美化不难吧（原 Q51）**：不难，是增量前端活。改 OSMD 选项（字体/配色/间距/小节号/多小节休止）+ CSS，不碰解析和判分逻辑，风险低、见效快，属于“花时间就能做”的工程。

**瀑布流和乐谱同屏还是选一个（原 Q49）**：选一个显示（切换），不是同屏。“画面”下拉有“瀑布流/五线谱”两项，`main.ts` 的 `updateViewMode()` 会隐藏另一个；导入 MusicXML 后默认自动切到五线谱，纯 MIDI 则用瀑布流。当前没有分屏模式（用户已标记要上下分屏，见第十二章）。

**“偏离初衷”怎么看（原 Q27）**：你的初衷在“运行时”其实已经实现——瀑布流/五线谱/曲库都在平板浏览器里跑，ESP 只做 USB Host/灯带/网页服务；真正偏离的是“交付形态”：你期待装在你练琴平板上的 App，实际拿到的是 ESP 自带的网页，而且视觉打磨确实不如 Openthesia/PTS。这是设计目标的取舍，不是代码质量崩塌。下一步选项：

- **A. 接受现状**：网页跑在平板上，功能齐全但观感朴素。
- **B. 走 Studio 路线**：现有 ESP 驱动与协议不动，另做一个装在你练琴平板上的 App/壳并重做 UI（难点与边界见第七章）。
- **C. 换/借鉴开源前端**：需处理 AGPL 许可与拓扑差异，工程量大（PTS 功能最接近但 AGPL 传染 + 走 WLED/浏览器 MIDI 拓扑，不驱动你这套 PX-S7000→ESP→APA102 链路；Openthesia 瀑布流最好但是 Windows 桌面端、不控 ESP；没有免费的完美替代）。
> 用户已确认方向（2026-08-07）：**选 B**——这套 Core 保留，平板端另做独立的视觉升级前端（Studio）；A/C 不再作为主要路线。

## 十一、代码体量与难度

> 合并原 Q37、Q38、Q39。行数按 2026-08-07 当前源码实测（近似值，随提交变化）。

**几千行代码到底干了啥（原 Q37）**：主要是“把音乐、练习、存储、协议做对”，不是画界面——这就是功能深、视觉素的原因。按 `../../web/src` 拆解（共 47 个 TS 文件约 7,650 行，含测试）：

- `musicxml.ts` 871 行：MusicXML/MXL 解析成统一时间线（拍号、变速、反复/跳转、移调）——最难的谱面正确性在这。
- `main.ts` 1,604 行：页面主流程/胶水（连 ESP、模式、视图、录制、校准、各面板）。
- `library.ts` 454 行：曲库 IndexedDB（SHA-256 去重、备份/恢复）。
- `practice.ts` 400 行：三种模式判分（Wait/Realtime/Follow、和弦持键、防作弊）。
- `analytics.ts` 281 行：练习历史、难点键、自适应建议。
- `protocol.ts` + `device.ts` + `clock-sync.ts`：WebSocket v6 客户端（鉴权/令牌/容错、硬件采集时间同步与网络抖动隔离）。
- 其他小模块：节拍器、移调、变速、目标同步、偏好、存储、MIDI 解析、OTA 更新、类型定义。
- 视觉文件：waterfall.ts 156 + sheet.ts 133 + style.css 162 + index.html 384 ≈ 835 行（占 ../../web/src 总量约 1/9，不到 1/5）。
- 固件 C++ 约 2,100 行、Python 脚本约 2,100 行另计。

**Codex 显示 19047 行、你说总共才一万多（原 Q38）**：计数口径不同，两边都对——19,047 是 Codex 会话的“新增行数”统计，一万多是“源码”行数，且各工具对“一行”的算法不同。实际盘点（本仓库，不含二进制）：

- 源码（TS/Python/C++/HTML/CSS/MJS）：约 1.3 万行；
- 全部文本文件（源码 + CAD 模型 STEP/STL 约 1.1 万行 + 文档 2,400 + 配置 3,300 + 测试夹具 600）：约 3.1 万行；
- 若把 PNG/JPG/gz 二进制当文本数，还会再多约 1.3 万行（无意义）。

所以：只看“代码”≈ 1.1–1.3 万行；把文档、配置、生成物都算上 ≈ 3 万行；19,047 大概率是 Codex 会话按自己规则统计的全部新增行（含文档/配置/夹具/生成资源）。不同工具算法不同，数字对不上是正常的，不代表代码少算或丢了。

**功能层难度 vs 开源 UI 层难度（原 Q39）**：功能层难度更大；但两者是两种不同的“难”。

- 功能层是“正确性难度”——做错就废：MusicXML 解析（拍号/变速/反复跳转/移调/弱起/断奏门控）、ESP32-S3 原生 USB Host 直读 PX-S7000 的 MIDI 固件、WebSocket v6 实时协议、判分防作弊（和弦持键/踏板/重叠音）及双手同步分析。G0 用 1016 语料 + 编译零警告 + 212 Web 测试验证，这部分“看不见”但最贵。
- 开源 UI 层是“工程量/审美难度”——做得多就好看：Openthesia 的 GPU 瀑布流（粒子/模糊拖尾/透视）约 7600 行 C# 主要就在干这个；PTS 的谱面正确性靠嵌入 webmscore（24 MB WASM）绕过，没有自研解析。
- 换位对比：我们补 UI 是纯前端、增量、不碰核心（200–400 行打磨即可见效，WebGL 可接近甚至超过 Openthesia）；反过来让他们补我们的功能层（自研 MusicXML 正确性 + 指定琴硬件链路 + 判分协议）要难得多，所以他们普遍选择不做或嵌入现成引擎。
- 一句话：我们的“难”做完了但看不见（正确性），他们的“难”是看得见但可加可减（工程量+审美）。你觉得“不如他们”，是因为差的恰好是看得见的那部分；核心难度其实在我们这边。

### 13.1 最终结论

1. **灯带用 SK9822，已买**。SK9822 和 APA102C 是同一类带时钟线灯带，可兼容；本项目按 SK9822/144 灯/米、5V、黑色、非防水规格买。不要混用 WS2812，也不要改买 200 灯/米。
2. **本机路线是“灯带自带裸线 + WAGO 按压接线端子 + 长线”自装免焊**。不找灯带/线束店代工，不焊灯带焊盘，也不买连接器来压线。

4. **不买**：Micro-Fit、XT30、XT60、DC5521 一进三出、黑色 PET 载体条。这些是默认找厂家方案里的连接器和辅助件，本机实际不用。

```text
电源：5V/5A → DC5521 圆头 → DC015 圆座 → 3A 保险丝 → WAGO 5V/GND 汇总

灯头：红=5V、黑=GND、绿=DATA、蓝=CLOCK
灯尾：红=5V、黑=GND；不接 DATA/CLOCK

H5：Micro-USB 公头供电线 → ESP32 的 USB-to-UART 口
H7：Micro-USB 公头供电线 → OTG Y 线第 3 个 Micro-USB 供电口
OTG Y 线 Micro-USB 公头 → ESP32 的 USB/OTG 口
钢琴：USB TO HOST（方形 USB-B）→ 打印机线 → OTG Y 线的 USB-A 母口
```

要点：

- H5 和 H7 是两根独立支路，不能合并成一根，也不能插反。H5 插开发板 `USB-to-UART`，H7 插 Y 线第三供电口；Y 线的 Micro-USB 公头插 ESP32 的 `USB/OTG` 口。
- 3A 保险丝放在电源入口、DC015 圆座之后、WAGO 汇总之前，串在 5V 正极上。这样保险丝保护后面所有支路，而不是只保护某一段。
- 1000µF 电容在灯带头尾并联到 5V/GND；100Ω 电阻分别串联在 DATA 和 CLOCK 信号线上。
- 74AHCT125N 先插 170 孔面包板测试；正式装盒前找手机维修店/来料焊接焊成 DIP-14 IC 座小板，别买 TXS0108/BSS138 模块代替。

### 13.4 WAGO 端子数量和为什么

按 `vendor-manufacturing.md` 第 1 节，实际使用：

| 用途 | 型号 | 数量 |
|---|---|---:|
| 两个 100Ω 电阻（DATA/CLOCK 各串一个） | WAGO 221-412（2 线） | 4 |
| H5/H7 的 5V 和 GND 合并 | WAGO 221-412（2 线） | 2 |
| 两个 1000µF 电容（每个电容的 5V/GND 各占一个） | WAGO 221-413（3 线） | 4 |
| 5V 汇总 | 独立公共配电端子；型号待到货按实际分支数确认 | 1 组 |
| GND 汇总 | 独立公共配电端子；型号待到货按实际分支数确认 | 1 组 |

已购数量：`WAGO 221-412 ×10`、`WAGO 221-413 ×10`。其中局部连接用途不变；公共 5V/GND 分配不能按旧数量公式处理。

为什么是这些：

- 100Ω 是**串联**在信号线上的，不是夹一次就完。每颗电阻有两只脚：一只脚接 74AHCT125 出来的信号线，另一只脚接去灯带的 DIN/CIN，所以 2 颗电阻用 4 个 2 线端子。
- 1000µF 是**并联**在供电点上的。每颗电容有正负两只脚，每只脚用 1 个 3 线端子同时夹“电容脚 + 电源线 + 灯带线”，所以 2 颗电容用 4 个 3 线端子。
- 5V 与 GND 都需要真正的公共节点。不同 WAGO 外壳不会因为并排或机械卡接而导通；不得把多根导线塞进同一夹孔。到货后按实际分支数选择 `221-415`、等效绝缘配电端子，或采用经过逐线表定义的桥接拓扑。

### 13.5 关键问答

**为什么不能直接用灯带，还要电容电阻？**

100Ω 电阻是保护 DATA/CLOCK 信号、减少振铃和短路风险；1000µF 电容是吸收全亮瞬间的电流尖峰，防止电源差时闪一下或复位。它们不是“必须装才亮”，但属于强烈建议，而且用 WAGO 夹上就行，不需要焊。

**APA102 和 SK9822 用哪个？有 200 灯/米的可以吗？**

用 SK9822（已买）。APA102C/SK9822 是同一类带时钟灯带，兼容设计；WS2812 不是。灯珠密度按 144 灯/米，88 键用 176 灯；200 灯/米不是文档规格，不换。

**灯带自带线够吗？为什么头尾分别有 4+2 根线？**

够。卖家成品通常就是“灯头 4 根、灯尾 2 根”，对应：灯头需要 5V/GND/DATA/CLOCK，灯尾只需要 5V/GND 补电。这正好接 WAGO 和长线，不需要自己焊灯珠焊盘。

**电容电阻必须焊吗？**

不用。买直插带长脚的电解电容和电阻，用 WAGO 夹线即可。电阻是串在信号线里，电容是并到电源线上；夹紧、不碰相邻脚，台面测试先验证，正式装盒前若想更稳可再找店焊。

**电容 470/680µF 可以吗？1/4W 电阻又是什么意思？**

你已按 1000µF 买，就按 1000µF 用；470/680 不是文档规格。耐压 16V/25V 都可以，不低于 10V。1/4W 只是常见小功率规格，信号电流很小，1/4W 足够。买电解电容，不买法拉电容。

**XT30、XT60、Micro-Fit、DC5521 一进三出要买吗？**

本机不买。XT30/XT60 是默认线束用的两针大电流连接器，Micro-Fit 是默认灯带端四针带锁连接器，DC5521 一进三出是默认方案里分电源用的。实际方案直接 WAGO 汇总，DC015 只是电源圆头插入的圆座。

**电源圆头买 2.1 还是 2.5？**

最终按 DC5521（5.5×2.1）买，DC015 圆座也按 2.1 配。2.5 是另一种规格，不要混用。

**保险丝放哪里？3A 和 5A 是什么关系？**

放电源入口：5V/5A 电源 → DC015 → 3A 保险丝 → WAGO 汇总。5A 是电源容量，保证灯带全亮有余量；3A 是保险丝保护上限，防止短路/过流烧线或起火。两者不是同一个东西，不能互相替代。玻璃管保险丝本身没线，买“保险丝座 + 引线”或“带座保险丝线束”，到手才有接线端子。

**74AHCT125N 裸芯片能不用焊吗？**

能先测试。DIP-14 直插芯片可以直接插 170 孔面包板，不焊也能点亮；170 孔面包板用来台面测试，不要求塞进 3D 盒。正式装盒前找手机维修店/来料焊接焊成 DIP-14 IC 座小板，尺寸小、能放进盒内。成品模块淘宝买不到，所以用“裸芯片 + 面包板测试 + 代焊小板”的路线。

**杜邦线买什么头？**

测试用买公对公和母对公若干即可；你已经买了就够。杜邦线只做面包板测试和排针连接，不是高电流主电源线。

**线材买硅胶线还是 1007 线？**

买硅胶线，软、耐弯，适合灯带走线；你已买的 20AWG 红黑硅胶线就是正确选择。

**线材怎么剪？**

20AWG 红/黑各 2 米：灯头 5V/GND 各约 0.5 米，灯尾 5V/GND 各约 1.6 米，盒内短接从余量取。26AWG 绿/蓝各 1 米：灯头 DATA/CLOCK 各约 0.5 米，余量备用。灯头短、灯尾长，是因为控制盒和灯头在同一侧，灯尾要绕到琴的远端。

**无痕固定带和 PET 要买吗？**

PET 载体条不买。用“拉伸移除式”无痕固定带直接固定灯带，不留胶；正式贴装前先做 24 小时表面测试，确认钢琴漆面没问题再正式装。

**电工胶带还要买吗？**

不优先买。WAGO 本身是绝缘按压端子，短接和接头不需要靠胶带；正式装盒时如果要用热缩管、护边条或扎带，再补购即可。

**为什么 `vendor-manufacturing.md` 要把本机方案单独列成第 1 节？**

因为本机已经实际走“自装免焊”路线，不再是默认“找厂家代工”方案的补充说明。两个方案应并列：第 1 节是本机真实方案，第 2 节是旧默认方案参考；所以不再叫 0.5，也不合进默认方案。

- 2026-08-07：问答“黑色 PET 最低 40 元，有必要吗”——结论：**可选件，不必要**；作用只是让灯带背胶不碰琴（护漆、可拆卸）；不买可用灯带自带背胶直接贴琴（先做 24 小时相容测试）；40 元偏贵，可换店/砍价（PET 或 PVC 均可），超 40 不值得。卡 D 已加“价格提醒”。
- 2026-08-07：问答“不粘贴、直接放在那里行吗”——结论：不行。安装面是竖直立面，灯带软、有自重会滑/掉，且不能碰活动琴键/盖红毡（M2/M3 安全底线）；但“不粘死”可行——用拉伸式无痕固定条（可拆、不伤漆，方案 B），沿长度多点固定；没有任何胶/夹子的机械方案不在设计内（琴键侧打印件 0 件）。
- 2026-08-07：问答“74AHCT125DR 可以吗”——芯片型号对（DR = SOIC-14 贴片封装 + 编带包装），但通常是裸芯片要自己焊，不符合“免焊接、不定制 PCB”；要买带排针的成品模块。判断标准：标题/详情是“74AHCT125 四路电平转换模块”成品小板即可，只卖芯片别买。
- 2026-08-07：问答“74AHCT125 选 DR 还是 N”——裸芯片里选 N（PDIP-14 直插，2.54 mm 脚距，新手可焊），DR 是贴片要转接板；但项目要的是成品模块（板上封装无所谓），只有自己买裸芯片焊才需关心封装。
- 2026-08-07：问答“什么模块？N 是模块吗？”——N/DR 只是裸芯片的封装后缀（直插/贴片），都不是模块；成品模块=带排针的小板（标题含“模块/板”，配图是小板），到手免焊接线。区分法：标题含“芯片/IC/散片”=裸芯片别买；含“模块/板”=可买。
- 2026-08-07：问答“有 TXS108/TXS0108 模块”——**别买**：双向自动方向检测，8 MHz SPI/APA102 时序易出问题；项目全链路（接线/100Ω 串阻//OE/验收）只按 74AHCT125 设计。继续搜 `74AHCT125 四路 电平转换 模块`；实在没有的退路是 74AHCT125N 直插+洞洞板自焊，也不选 TXS0108。
- 2026-08-07：问答“像螃蟹一样几条腿的芯片是吗”——是：DIP-14 直插（14 脚，每边 7 脚）就是 74AHCT125N，属“裸芯片+洞洞板自焊”退路；首选仍是带排针的成品模块（免焊）。接线按 docs/hardware.md 灯带接线图。
- 2026-08-07：问答“螃蟹芯片不是有脚吗，为啥还要焊”——有脚只是接口，必须和电源/信号真正连上才工作；DIP 芯片要么焊（洞洞板/IC座，永久安装）要么插面包板（免焊但松，只适合测试）。成品模块=厂家已焊好，排针是接线端子，免焊。
- 2026-08-07：问答“什么叫模块？插杜邦线那种？”——模块=厂家已焊好芯片、带排针/端子的小板，到手免焊；本工程 ESP32↔74AHCT125 之间按 docs/harness.csv 用 24AWG 红黑线，端接写的是“模块端子或焊接加热缩”，不是杜邦线；裸芯片没有端子所以必须焊，模块有端子可以拧/夹/插线头。认准标题含“模块/板”、配图是小板的成品；“芯片/IC/散片”不买。
- 2026-08-07：问答“那不就是能直接插杜邦线那种吗？”——一半对：模块排针是 2.54 mm 标准针距，杜邦线母头物理上确实能插；但杜邦线是测试用临时线（细、松、无锁扣），正式装机不用它，工程按 docs/harness.csv 用 24AWG 红黑线接“模块端子或焊接加热缩”。买时看配图：带绿色螺丝端子的模块最省事（线头塞进去拧螺丝，连杜邦都不用）；只有排针的也能用，正式接法是把线头绕/拧在针脚上或焊+热缩。
- 2026-08-07：问答“那 24AWG 红黑线不是得让线束定制的人做吗？我上哪弄”——不是大活：H6 只有两段 12 cm 短线（ESP32↔74AHCT125 供电用）。两个来源任选：① 下卡 B 线束单时让店家顺手做（他们本来就有 24AWG 线，两小段几乎不加钱，收货直接接模块端子）；② 自己买一小卷硅胶线（`硅胶线 24AWG 红黑`，本来就在购物清单里，15–35 元）剪两段 12 cm、剥 5 mm 铜丝拧进模块螺丝端子，2 分钟，不焊不压端子。盒内还有 GPIO11/12→A1/A2 两根信号线（harness.csv 未单列，属盒内短接），装机时用细线接端子即可。
- 2026-08-07：问答“引脚不是得杜邦线吗？端子是啥”——引脚/针脚只是金属接触点，不是“必须杜邦线”；杜邦线只是给排针设计的一种带插头的测试线。端子=给电线留的连接口统称：螺丝端子（线头放进去拧螺丝夹紧，免焊免杜邦）、排针（可插杜邦线/绕线/焊）、焊盘（必须焊）。模块带绿色螺丝端子时，直接把剥好的线头塞进去拧紧即可。
- 2026-08-07：问答“我没找到模块，你查查淘宝”——核查结论：74AHCT125 成品小板国内确实少见（烂大街的是 BSS138/TXS0108 双向模块，都不能用；国际成品是 Adafruit 1787，国内多为代购/克隆）。裸芯片很好买：74AHCT125N（DIP-14 直插）约 2–5 元。找不到模块就走“买芯片让店家焊”路线：74AHCT125N + DIP-14 IC 座 + 洞洞板 + 排针，让卡 A/B 线束店或手机维修店代焊成小板（引出 VCC/GND/A1/A2/Y1/Y2，OE1/OE2 板内直接接 GND），人工约 10–30 元，到手等同成品模块。注意别买 74HCT125N（少个 A，非文档规格）。
- 2026-08-07：问答“你看看淘宝有没有”（实查核实，更新上一条）——淘宝在售结果里**没有 74AHCT125 的常驻成品模块**：烂大街的成品是 TXS0108E 8 路双向模块（约 2–7 元，不可用）；74AHCT125 只以裸芯片在售（74AHCT125N DIP-14 直插约 2–5 元 / 74AHCT125DR 贴片）；成品小板只有海外 Adafruit 1787，国内多为代购/克隆、可碰运气搜“Adafruit 1787”但别依赖。结论维持：免焊的 74AHCT125 成品模块淘宝买不到，走“74AHCT125N 裸芯片 + 店家代焊成小板”（人工 10–30 元，到手等同成品模块，见上一条），不要退而买 TXS0108E。

- 2026-08-07：问答“买 74AHCT125N 不焊、直接接线行吗？要接几根线？”——能通但不建议装机：裸芯片 14 根脚是光秃秃金属腿，脚距 2.54 mm，直接拧线头上去一碰就松、易与邻脚短路，只适合测试；真正免焊又稳的是插面包板+跳线（不焊），装机仍建议店家代焊成小板。用两路（DATA/CLOCK）需接 8 个脚 = 6 根外来线 + 2 根 OE 短接：VCC(14)→5V、GND(7)→GND、1A(2)←ESP32 DATA、2A(5)←ESP32 CLOCK、1Y(3)→100Ω→灯带 DATA、2Y(6)→100Ω→灯带 CLOCK，1OE(1)/2OE(4) 接 GND（低电平使能）。
- 2026-08-07：问答“电容电阻必须有吗？找不到人给我弄”——都不是“必须有”，是强烈建议：100Ω×2（DATA/CLOCK 串阻）阻尼振铃+短路保护，盒内到灯带约 40cm 短距不装大概率也正常但失去保护；1000µF×2（灯带首尾）吸收全亮瞬间电流尖峰，不装可能全白瞬间闪一下、电源差时 brownout。两者都是直插元件（BOM 写“已焊引线并绝缘”），用端子/缠绕免焊可接，不需要单独找人焊。真正建议焊的只有三处：灯带裁切首尾注电、两根 100Ω 串入信号线、74AHCT125 芯片。解决“找不到人”：找卖灯带的淘宝店，下单时把 docs/vendor-order-template.md 发给店家，要求“裁切+首尾注电+串 100Ω+并联电容”，工费几元到十几元一次搞定；芯片再让同一家或手机维修店代焊成小板（10–30 元），或淘宝搜“来料焊接/代焊”。安全底线不可省：3A 保险丝、公共地、H7（first-build.md 明令不得跳过）。
- 2026-08-07：问答“电容电阻买直插的，线束那些呢？”——电容电阻是散件自己买直插；线束不是散件，是“带插头的成品线”，直接下单买“预压/带线”版本即可（不用压端子、不用焊）。现成件：DC5521 母 一分三 15–35、Micro-Fit 3.0 4P 公母预压线 15–35、XT30 公母带线 8–15、DC5521→Micro-USB 供电线 ×2 各 10–30、3A 保险丝座线束 5–15、20AWG 红黑硅胶线/26AWG 绿蓝信号线。唯一特例是 1.6m 的 H3 长线（现成 XT30 线一般 10–30cm，需买 1.5–2m 长线或让线束店压端子）。买直插件后自己动手的免焊点只有 3 个：100Ω 串入 DATA/CLOCK、1000µF 并到首尾注电点、公共地用 2–4 位接线端子排汇聚。两条路：省事=灯带店做卡 A+线束店做卡 B（整组 40–110 元）；省钱=成品线全自己买（约 80–150 元）+3 个免焊点自己接。
